開発ハーネスのモデル

AIに実装を任せながら、仕様どおりに作れているかを確かめ、失敗を次の手順と検査に戻すための要素と関係。アプリの中身に依存しない骨格だけを描いています。

状態：下書き（2026-10-26） 出典：公式資料・日本語記事・論文の調査3件 議論したセッション

3つの流れ

  • 作るIssue → 仕様とAC → テスト → PR。検査と人の確認を通って取り込む。
  • AIを動かす指示・規約・手順書を読み、権限とフックの枠の中で作業する。会話ログは外へ書き出す。
  • 育てる振り返りで、繰り返した失敗だけを規約・手順書・検査・フックに戻す。

1. 作る：仕様から取り込みまで

2. AIを動かす：読むもの・縛るもの・残すもの

3. 育てる：振り返りから戻す先

研究から引いた注意

  • AIがテストを書き換えて通す行動は、ベンチマークで繰り返し観測されている。テストファイルの変更は検出して、理由を求める。ImpossibleBench arXiv:2510.20270、EvilGenie arXiv:2511.21654
  • 「TDDでやれ」と手順だけを指示すると、回帰がかえって増えた。どのテストが関係するかという情報を渡す方が効いた。TDAD arXiv:2603.17973
  • 指示ファイルの効果は研究で割れている。所要時間とトークンが減った研究と、成功率が上がらずコストが増えた研究がある。中身は「このレポ特有の約束」に絞る。arXiv:2601.20404 / arXiv:2602.11988
  • マージされたかどうかは品質の指標にならない。不採用の多くはエージェントの誤り以外の理由だった。arXiv:2605.22534（MSR 2026）

マージ率を指標にする品質を表さない採用しない
