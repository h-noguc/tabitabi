# 0008 CI の運用

状態: 一部決定（2026-10-26）
判断者: 自分
議論: https://claude.ai/code/session_01RRsWb1PMfgKNATkiZKYMQQ

## 決定
- **何を検査するか**: 型チェック、Lint・整形、単体テスト、ビルド。DB の統合テストとブラウザ操作のテストは、対象ができてから足す
- **いつ走らせるか**: PR ごとを関門にする。main への push でも同じ検査を事後確認として回す（スピードには影響せず、別々に緑だった PR の組み合わせで main が壊れるのを拾える）
- **権限と秘密**: CI の権限は読み取りのみ。本番の秘密情報と本番 DB は渡さない。テスト用 DB は CI の中で使い捨てにする
- **必須チェック**: 上の4つ。GitHub Pro にしてルールセットで強制する（0009）
- **誰が直すか**: PR を作ったセッション自身。PR の状態を購読し、CI が落ちたら起きて直す。レビュー役（0007）は指摘だけで、直さない

## 提案（手順書 fix-ci の中身）
1. 失敗したジョブの、最初の意味のあるエラーを読む
2. 原因を分ける: この PR の不具合 / 準備不足 / main でも落ちている / 実行基盤の一時的な失敗
3. 同じコマンドで手元に再現する
4. 原因に対して最小の修正。不具合なら、修正前に落ちて修正後に通るテストを足す
5. 落ちた検査、次に周辺の検査を通してから push する
6. 原因に対する修正を3回試しても進まなければ止まり、何が落ちたか・試したこと・仮説・決めてほしいことを PR にコメントする

## 提案（仕組みで止めること）
| 禁止 | 止める仕組み |
|---|---|
| テストの削除・skip・期待値を実装に合わせる | フックでテストファイルの変更を検知し理由を求める。レビュー役がテストの差分を見る。「要確認」ラベル |
| CI 設定を緩める | `.github/workflows/` の変更に「要確認」ラベル |
| `--no-verify` | フックで禁止 |
| 原因を調べずに再実行 | 再実行は実行基盤の失敗のときに1回だけ。「flaky」は原因と認めない |

CI と同じ検査を、セッションの終了前（Stop フック）か push 前（Lefthook）に手元で回し、CI で落ちるのを環境差による失敗に絞る。
